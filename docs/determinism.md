# 재현성 — 이 저장소는 오랫동안 결정적이지 않았습니다

**한 줄**: 같은 토픽을 두 번 검색하면 다른 논문 목록이 나왔습니다. 원인은 DuckDB BM25 의
정렬이었고, 2026-08-13 에 고쳤습니다.

> **2026-08-13 이전에 뽑은 결과는 재현되지 않습니다.** 결론은 안 바뀌지만(차이가
> nDCG 1e-5 수준) 숫자를 그대로 다시 얻을 수는 없습니다. 그래서 170토픽 평가를
> 다시 돌렸습니다.

## 어떻게 발견했나

성능 수정 후 "결과가 그대로인지" 확인하려고 저장된 170토픽 결과와 대조했습니다.

```
dense only   sid=1,2,3   일치
+bm25        sid=1,2,3   일치
+freshness   sid=1,2,3   일치
+facets      sid=1,2,3   **불일치**
```

`+facets` 만 어긋났습니다. **제 수정 탓인 줄 알았습니다.**

`git stash` 로 수정을 걷어내고 같은 토픽을 원래 코드로 돌렸더니 — **원래 코드도
어긋났습니다.** 게다가 두 실행이 서로도 달랐습니다(sid=1 이 0.218077 vs 0.218074).
코드 차이라면 이럴 수 없습니다.

같은 코드로 같은 토픽을 두 번 돌려 확인했습니다:

```
실행 1: id 목록 해시 9a4c6df42362
실행 2: id 목록 해시 cdc9a30627d5
→ 다름 = 비결정적
```

## 범인을 계층별로 좁히기

`+facets` 만 어긋난 것이 단서였습니다 — 다른 세 설정은 쿼리가 **1개**, facet 은 **36개**.
쿼리가 많을수록 흔들릴 자리가 많다는 뜻입니다.

| 후보 | 결과 |
|---|---|
| GPU 임베딩 (cuBLAS 비결정성) | **결백.** 2회 bitwise 동일, 최대차 0.000e+00 |
| `PYTHONHASHSEED` | **결백.** 같은 프로세스 안에서도 재현됨 |
| FAISS `IndexFlatIP` | **결백.** `dense_search` 2회 완전 동일 |
| **DuckDB BM25** | **범인.** `lexical_search` 2회 다름 |

> 처음에 GPU 임베딩과 FAISS 동점 처리를 원인으로 지목했는데 **둘 다 틀렸습니다.**
> 계층별로 격리해서 재기 전까지는 추정이었습니다.

## 원인의 정확한 형태

`lexical_search` 를 두 번 부른 결과:

| 쿼리 | 첫 불일치 순위 | 반환 집합 |
|---|---|---|
| 0 | 142 / 2000 | 동일 (순서만) |
| 1 | 171 / 2000 | 동일 |
| 2 | **60 / 2000** | **다름 — 논문 자체가 바뀜** |

상위 300편으로 좁혀 정밀하게 재면:

| | |
|---|---|
| 반환 집합 | **완전히 동일** (300/300) |
| 같은 논문의 점수 최대차 | **8.882e-16** |
| 순서 | **다름** |
| `SET threads TO 1` | **결정적** |

즉 DuckDB 가 병렬로 누적하면서 **부동소수점 마지막 비트가 흔들리고**,
`ORDER BY score DESC` 에 **동점 규칙이 없어** 그 순서가 실행마다 갈립니다.

`top_k` 경계에서는 순서를 넘어 **어느 논문이 컷에 들어오느냐**까지 바뀝니다
(2,000편 중 60등에서 다른 논문 유입). 그게 facet 12~16개를 거쳐 RRF 로 증폭됩니다.

## 수정

```sql
ORDER BY round(score, 9) DESC, paper_id
```

`SET threads TO 1` 로도 없어지지만 그건 BM25 를 느리게 만듭니다. 반올림 + tie-break 는
**공짜**이고, 9자리는 BM25 점수의 의미 있는 정밀도를 한참 넘습니다 — 점수 차가 1e-9 인
두 논문은 실질적으로 동점입니다.

```
BM25 켠 전체 검색 3회: 동일  ['3b2c6c93dce9', '3b2c6c93dce9', '3b2c6c93dce9']
```

## `lexical_search` 의 raw 점수는 아직 흔들립니다 — 무해합니다

반환 튜플의 float 은 여전히 1e-16 만큼 달라집니다. 순서는 고정됐지만 값은 아닙니다.

**이건 문제가 되지 않습니다.** 이 파이프라인은 처음부터 **융합에 순위만 씁니다**
(RRF). 함정 4번 — "쿼리 벡터가 비정규화라 쿼리 간 점수 비교 불가" — 때문에 세운
원칙인데, 여기서 예상 못 한 값을 했습니다. 점수가 흔들려도 전체 검색은 결정적입니다.

## 무엇이 원래 결정적이었나

| | |
|---|---|
| 쿼리 임베딩 (gte-large, GPU) | 2회 bitwise 동일, 최대차 **0.000e+00** |
| FAISS `dense_search` | 2회 완전 동일 |
| facet 분해 | 디스크 캐시 → 호출 0회 |
| 온라인 백엔드 (arXiv·S2) | 디스크 캐시 |

**LLM 호출이 캐시되는 것과 파이프라인이 결정적인 것은 별개입니다.**
`facets.py` 첫머리에 "결과는 디스크 캐시라 ... 그래서 실험도 결정적입니다"라고 적혀
있었는데, 앞 절은 맞고 뒤 절은 틀렸습니다.

## 병렬 실행 시 주의 — facet 캐시 덮어쓰기

`decompose` 는 캐시가 없을 때만 LLM 을 부르고 씁니다. 그런데 **두 프로세스가 같은
토픽을 동시에 잡으면** 각자 부르고 각자 씁니다. `temperature=0.2` 라 두 응답이 다르고,
나중 쓰기가 먼저 것을 덮습니다.

`os.replace` 로 원자적 쓰기를 하므로 **파일이 깨지지는 않지만**, 평가가 A 를 읽은 뒤
프리웜이 B 로 덮으면 그 평가는 재현되지 않습니다.

프리웜을 병렬로 돌릴 때는 `SHARD`/`NSHARDS` 로 **서로 다른 토픽만 맡게** 하세요.
평가 본체와 동시에 돌리는 것은 이 위험이 있습니다.
