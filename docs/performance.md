# 성능 — 검색 1회 227초에서 2.6초로

**한 줄**: 병목은 dense 검색도 GPU 도 아니었습니다. **DB 조회를 두 번, 그것도 해시
조인을 못 쓰는 형태로** 하고 있었습니다.

**검색 품질은 바뀌지 않았습니다** — 설정 4개 × 토픽 12개로 nDCG·R@1500 차이 전부 0.

## 증상

facet 을 켠 검색 하나가 이만큼 걸렸습니다 (n_papers=1500, 컷오프 없음, GPU 단독):

| | |
|---|---|
| facets + freshness (BM25 켬) | **227.8초** |
| facets + freshness (BM25 끔) | **114.6초** |

문서에는 "12~15초"라고 적혀 있었습니다. 그 값은 평가 실행에서 역산한 것인데, 평가는
날짜 컷오프로 후보를 줄이고 있었습니다. **성능은 산정하지 말고 재세요.**

## 두 번 헛짚었습니다

프로세스를 보니 GPU 사용률 0%, CPU 누적 46분(멀티스레드). 여기서 **계산 문제라고
단정**한 것이 잘못이었습니다.

**헛짚음 ①** — 로그에 매번 찍히던 이 줄을 잡음으로 여기다 뒤늦게 발견했습니다:

```
Could not load library with AVX512 support: No module named 'faiss.swigfaiss_avx512'
Could not load library with AVX2 support:   No module named 'faiss.swigfaiss_avx2'
Loading faiss.        ← SIMD 없는 일반 빌드로 폴백
```

CPU(AMD EPYC 9124)는 avx512f 를 지원하는데 `faiss-cpu 1.15.0` 은 `_swigfaiss.abi3.so`
하나뿐이라 SIMD 변형이 없습니다. **사실이지만 무관했습니다.**

**헛짚음 ②** — 그래서 GPU 로 옮기면 되겠다고 판단했습니다. `faiss-gpu==1.15.0`
(Meta AI Research 공식, MIT)이 이 머신에서 실제로 **동작합니다** — CUDA 12.6 런타임이
550.120 드라이버에서 돕니다. 격리 venv 로 확인했습니다.

그런데 재보니:

```
인덱스 로드 2.4s   ntotal=908,819  d=1024
CPU (faiss-cpu, SIMD 없음)   0.145초     ← 쿼리 16개 × top_k 2000
GPU (faiss-gpu)              0.016초     (8.9배)
```

**dense 검색은 전체 227초 중 0.145초, 0.1% 였습니다.** GPU 로 8.9배를 얻어도 0.13초가
줄 뿐입니다. **CPU 가 바쁘다고 계산 문제인 것은 아닙니다.**

## 실제 병목 — 단계별로 재기

`StageStat.elapsed_s` 를 찍자 바로 드러났습니다.

```
--- BM25 켬  합계 218.9s ---          --- BM25 끔  합계 138.2s ---
  meta          90.1s (48,214건)        meta          60.7s (33,753건)
  S5 dedup      90.0s                   S5 dedup      60.5s
  S2 dense      30.8s                   S2 dense      16.1s
  S3 lexical     6.7s                   S6 freshness   0.8s
  S6 freshness   1.1s                   S4 rrf         0.1s
  S4 rrf         0.2s
```

`meta` 와 `S5 dedup` 이 **82%**. 그리고 둘의 시간이 90.1 / 90.0 으로 거의 같은 것이
단서였습니다 — **같은 일을 두 번** 하고 있었습니다.

## 원인 ① 조인 조건의 `OR` 가 해시 조인을 막고 있었습니다

```sql
-- 문제
ON p.paper_id = w.want OR p.base_id = w.want_base
```

같은 id 집합으로 잰 값:

| 건수 | `OR` 조인 | 등호만 | **분리 (수정)** |
|---|---|---|---|
| 1,000 | 0.48s | 0.05s | 0.08s |
| 5,000 | 2.09s | 0.18s | 0.15s |
| 15,000 | 8.85s | 0.24s | **0.16s** |
| 35,000 | 19.25s | 0.33s | **0.20s** |
| 50,000 | **20.05s** | 0.23s | **0.23s** |

`OR` 는 **초선형**, 분리는 평평합니다. 5만 건에서 **87배**.

1,000건에서는 0.48초 대 0.08초라 눈에 안 띕니다. **facet 을 켜서 후보가 수만 편이
되어야 드러납니다.**

**수정**: 등호 조인으로 맞춘 뒤 **못 맞춘 것만** base_id 로 한 번 더 조인.
base_id 폴백은 그대로 유지됩니다.

### 이건 두 수정이 겹쳐서 생긴 상처입니다

원래 등호 조인이었습니다. 그래서 코드 주석의 "pyarrow 조인이면 0.1초"가 **그때는
맞았습니다.** 나중에 "스노우볼링이 논문을 0편 기여하던" 버그를 고치며
`OR p.base_id = w.want_base` 를 덧붙였고, **그때 최적화가 조용히 죽었습니다.**

성능 주석은 옛 값 그대로 남아 있어 아무도 그 자리를 의심하지 않았습니다.

> **교훈: 성능 주석에는 언제 잰 값인지 남기세요.**

## 원인 ② 같은 수만 편을 두 번 조회했습니다

`S5 dedup` 이 제목을 얻으려 `get_papers` 를 부르고, `meta` 단계가 **거의 같은 집합에
또** 부릅니다.

코드 주석은 "후보 전체를 조회하면 비싸므로 최종 목록의 3배까지만"이라는데,
실제 기본값은 `title_window = None`, `rank_window = None` — **둘 다 "전량"** 입니다.
의도가 기본값에 반영돼 있지 않았습니다.

**수정**: S5 가 가져온 것을 재사용하고 모자란 것만 채웁니다.

> ⚠ **순서를 보존해야 합니다.** `freshness=False` 면 `candidates` 순서가 **곧 최종
> 랭킹**입니다(RRF 순서가 fused → deduped → window → fetched 로 흘러옵니다).
> 재사용분을 뒤에 몰아 붙이면 기준선 실험의 랭킹이 통째로 바뀝니다. 처음 고칠 때
> 이걸 놓쳐서 다시 썼습니다.

## 결과

|---|---|---|
| AutoSurvey 검색 4회 | **약 8분** | **약 10초** |

"이렇게 끼우세요"라고 문서에 써놓고 실제로는 쓰기 어려운 상태였습니다.

## 품질이 안 바뀌었는지 확인

성능 최적화가 랭킹을 바꾸면 그건 버그입니다. 저장된 170토픽 결과와 대조했습니다:

## 실측 요약 (GPU 단독, n_papers=1500, 컷오프 없음)

| | 값 |
|---|---|
| 백엔드 생성 + 첫 검색 | 16초 (FAISS 3.7GB 로드) |
| **검색 1회 (권장 설정)** | **2.6초** (n=5, 2.1~3.1) |
| 검색 1회 (facets + BM25) | 13.9초 (n=5, 9.9~26.9) |
| 검색 1회 (facets 끔) | 2.7초 |
| FAISS 16쿼리 × top_k 2000 | 0.145초 (CPU) / 0.016초 (GPU) |
| 메타 조회 5만 건 | 0.23초 (등호) / 20.05초 (`OR`) |

> **GPU 를 나눠 쓰면 크게 늘어납니다.** 같은 카드에서 검색 작업 두 개를 같이 돌렸더니
> 검색 하나가 **14배** 느려졌습니다. 시간을 잴 땐 `nvidia-smi` 로 카드를 비우세요.

## faiss-gpu 를 도입하지 않은 이유

동작은 확인했습니다. 그런데 **FAISS 가 검색 시간의 0.1%** 라 8.9배를 얻어도 0.13초가
줄 뿐입니다. 대신 격리 환경 관리와 GPU 3.7GB 상주라는 비용이 붙습니다.

병목이 다른 데로 옮겨가면 그때 다시 볼 문제입니다.
