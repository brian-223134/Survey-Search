# 함정 12가지 — 전부 실제로 밟은 것들

대부분 **"돌아가는 것처럼 보이면서 아무 일도 안 하던"** 종류입니다. `stats` 경고와
단계별 계측이 없었으면 못 찾았습니다. 몇 개는 두 번 밟았습니다.

## 데이터·인덱스

**1. FAISS id 는 1-based**
0-based 로 가정하면 한 칸 밀린 논문이 **조용히** 반환됩니다. 예외도 경고도 없습니다.
`tests/test_faiss_mapping.py` 의 의미 수준 왕복 검증 10/10 으로 고정했습니다.

**2. `faiss_id − 1` 은 행 번호가 아닙니다**
`id_map` 이 1..N 의 **순열**이라 441,842개가 어긋납니다. 인덱스가 세 덩어리를 다른
순서로 이어 붙여 만들어진 흔적입니다. 저장된 문서 벡터를 꺼낼 땐 `build_id_to_row()`
필수. id 로만 접근하는 일반 검색 경로는 무관합니다.

**3. `citation_count` 가 문자열입니다**
캐스팅 안 하면 `'9' > '175503'`. 랭킹이 조용히 망가집니다.

**5. `date` 는 최신 버전 갱신일입니다**
v1 게시일이 아닙니다. 2007년 논문이 2025년에 개정되면 '최신'으로 보입니다.
나이 계산은 `submitted_date`(arXiv id 의 `YYMM` 에서 유도) 기준.
날짜 컷오프 탈락률이 7.07% → 6.75% 로 바뀝니다.

**6. Semantic Scholar 는 버전 없는 id 를 줍니다**
우리 DB 키는 `2401.12345v2`, S2 는 `2401.12345`. `get_papers` 에 base_id 폴백이 없으면
**스노우볼링이 0편 기여하고도 조용히** 지나갑니다.

## 점수와 랭킹

**4. 쿼리 벡터가 비정규화입니다** (norm ≈ 24)
한 쿼리 안의 순위는 멀쩡하지만 **쿼리끼리 점수를 비교할 수 없습니다.**
순위 기반 RRF 가 이 인덱스에서는 선택이 아니라 **필수 조건**입니다.

**8. cross-encoder 점수도 쿼리 간 비교 불가입니다** — 4번과 같은 함정, 다시 밟음
facet 쿼리별 평균이 **20배** 차이 납니다:

| facet 쿼리 | 평균 |
|---|---|
| rationale extraction machine reading comprehension | 0.127 |
| chain-of-thought prompting reading comprehension | **0.006** |

그래서 `chain-of-thought` facet 에서 **1위**인 논문이 `rationale extraction` facet 의
**중위권** 논문보다 낮은 점수를 받습니다. 결과적으로 "관련성"이 아니라
**"어느 facet 소속인가"로 정렬**됩니다. → [reranking.md](reranking.md)

> **4번과 8번이 같은 함정입니다.** 이 파이프라인에서 서로 다른 쿼리로 매긴 점수를
> 직접 비교하는 곳이 있으면 거의 항상 버그입니다 — 순위로 바꿔 RRF 로 합치세요.

**7. MMR 풀이 커지면 다양성이 관련성을 압도합니다**
관련성을 풀 안에서 정규화하기 때문입니다. → [diversity-mmr.md](diversity-mmr.md)

**9. `rerank_config.top_n <= n_papers` 면 재랭킹이 무의미합니다**
최종 *집합* 이 안 바뀌고 순서만 바뀌어, 켠 실험과 끈 실험이 recall 로 구분되지
않습니다. `stats` 에 경고가 뜹니다.

## 인프라

**10. `urlopen(timeout=)` 은 호출 전체의 상한이 아닙니다**
소켓 연산 **1회**의 상한입니다. OpenRouter(Cloudflare 뒤)는 생성이 긴 요청에
**10초마다 912바이트** keep-alive 를 흘려보내는데, 그때마다 읽기가 성공하니 타이머가
초기화되고 90초 상한이 **영영 발동하지 않습니다.** 재시도 횟수도 예외가 안 나니
소용없습니다.

실제로 170토픽 평가가 **CPU 0% · GPU 0% 로 19분** 정지했습니다. 프로바이더가 19분 뒤
빈 응답을 돌려주고서야 풀렸습니다.

진단은 이렇게 했습니다:

```bash
cut -d' ' -f14,15 /proc/<pid>/stat   # CPU 시간이 20초에 0.01초만 늘어남
ss -tnp | grep <pid>                 # 소켓은 ESTAB 로 살아 있음
grep rchar /proc/<pid>/io            # 정확히 10초마다 912바이트씩
```

**"살아 있는데 아무것도 안 하는" 상태는 `pgrep` 만으로는 절대 안 보입니다.**
벽시계 상한(`_read_with_deadline`)이 따로 필요합니다.

**11. 조인 조건의 `OR` 는 해시 조인을 죽입니다**
`ON a = x OR b = y` 는 사실상 중첩 루프가 됩니다.

| 건수 | `OR` | 등호만 |
|---|---|---|
| 1,000 | 0.48s | 0.05s |
| 50,000 | **20.05s** | 0.23s |

1천 건에서는 눈에 안 띄는데 **초선형**이라 후보가 수만 편이 되면 파이프라인을
잡아먹습니다. → [performance.md](performance.md)

> **이건 두 수정이 겹쳐서 생긴 상처입니다.** 원래 등호 조인이었고(주석의 "0.1초"가
> 그때 값), 나중에 6번을 고치며 `OR` 를 덧붙이면서 최적화가 **조용히 무효**가 됐습니다.
> **성능 주석에는 언제 잰 값인지 남기세요.**

**12. DuckDB `ORDER BY` 에 동점 규칙이 없으면 비결정적입니다**
BM25 점수가 부동소수점 끝자리(**8.9e-16**)만큼 흔들리면 순서가 갈리고, `top_k`
경계에서는 **어느 논문이 들어오느냐**까지 바뀝니다. → [determinism.md](determinism.md)

## 반복해서 드러난 형태

이 열둘을 다시 보면 몇 가지 형태가 반복됩니다.

**① 조용한 실패가 시끄러운 실패보다 비쌉니다.**
1·3·5·6·11·12 는 전부 예외 없이 잘못된 결과를 냅니다. "무음 폐기 금지" 원칙
— 필터·윈도우·컷오프가 버린 건수를 반드시 세어 `stats` 에 남긴다 — 이 실제로
버그를 다섯 번 잡았습니다.

**② 같은 함정을 형태만 바꿔 다시 밟습니다.**
4번(dense 점수)을 알고도 8번(cross-encoder 점수)을 밟았습니다. 원칙을 알고 있어도
새 코드에서 적용을 잊습니다.

**③ 주석에 적힌 성능은 그 코드의 성능이 아닐 수 있습니다.**
11번이 그렇습니다. 각각은 옳은 수정 두 개가 겹치면서 생겼습니다.

**④ 자원 사용률로 원인을 추정하면 틀립니다.**
CPU 가 바쁘다고 계산 문제가 아니었습니다(11번은 DB 조회). 단계별로 재기 전까지는
전부 추정입니다.

## 부록 — 호스트 어댑터에서 밟은 것 (2026-08-13)

SurveyForge 호스트에 실제로 꽂기 전 코드를 양쪽 대조해서 찾았습니다. 위 열둘과 같은
성격 — **예외 없이 결과만 틀리는** 종류입니다.

**13. 호스트가 필터를 `filter=` 가 아니라 `**` 로 펼쳐 넘깁니다**
`get_index_filter` 가 `{'id_selector': IDSelectorArray}` 를 돌려주고 호출부는
`**index_filter` 로 펼칩니다. `filter=None` 시그니처만 두면 `id_selector` 가
`**kwargs` 로 빨려 들어가 **조용히 버려집니다.** 잃는 것은
`paper_id_cutoff` 시간 게이트와 writer 의 2단계 좁히기 — 둘 다 무효가 되는데
아무 신호가 없습니다.

> **어댑터를 쓸 때는 호스트의 *호출 형태*까지 봐야 합니다.** 시그니처가 맞는 것과
> 인자가 도착하는 것은 다릅니다.

**14. 인용 검증 경로에는 순서 계약이 있습니다**
호스트가 `zip(citations, ids)` 로 인용-논문을 맞춥니다. 즉
**쿼리 N개 → id N×top_k, 입력 순서**가 계약입니다.

이전 어댑터는 N개를 `" ; "` 로 이어 붙여 **한 번** 검색하고 랭킹 순 목록을 돌려줬습니다.
예외가 나지 않으면서 본문의 `[1]` 이 다른 논문을 가리키는 서베이가 편당 $2 에 나오고,
A/B 평가가 전부 그 매핑 위에서 계산되므로 **비교 자체가 무의미해집니다.**

지금은 쿼리별로 검색하고 **길이 계약을 어댑터 안에서 검사**합니다(어긋나면 예외).
필터 때문에 후보를 못 찾은 쿼리는 정렬을 지키려고 메우되 **그 사실을 `stats` 에
남깁니다** — 조용히 메우면 같은 종류의 버그가 됩니다.

둘 다 `tests/test_adapter_surveyforge_wiring.py` 가 붙잡습니다. 호스트가 실제로 보내는
`faiss.IDSelectorArray` 로도 검사합니다.
