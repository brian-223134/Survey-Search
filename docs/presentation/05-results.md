# 5. 결과 — 정답 집합으로 잰 것

## 평가를 어떻게 설계했나

문서 초안 단계에서는 "SurGE 벤치마크 구현이 미공개라 정량 평가 보류"로 적어 뒀는데,
**직접 확인하니 그 전제가 틀렸습니다.**

[SurGE](https://github.com/oneal2000/SurGE) 의 `data/surveys.json` 에 GT 서베이 205편이
있고, 각각 `survey_title`(토픽)과 `all_cites`(그 서베이가 실제로 인용한 논문 목록)를
가집니다.

> **서베이가 인용한 논문 집합이 곧 그 토픽의 정답입니다.**

README 가 언급하는 `queries.json` 은 배포본에 없지만 없어도 됩니다.

### 정답 집합 구축

SurGE 코퍼스에는 arXiv id 가 없어서 **정규화 제목**으로 연결했습니다.

| | |
|---|---|
| 인용 13,485편 중 연결 | **12,324편 (91.4%)** |
| 서베이별 매칭률 중앙값 | **92.1%** |
| 사용 토픽 | 205편 중 **170편** (all_cites 없음 9편, 정답 10편 미만 26편 제외) |
| 토픽당 평균 정답 | **72편** |

### 날짜 컷오프가 **필수**입니다 — 발표에서 꼭 짚을 것

GT 서베이는 2019~2023년입니다. **2020년 서베이는 2021년 논문을 인용할 수 없습니다.**

컷오프 없이 평가하면 우리 파이프라인이 최신 논문을 밀어주는 만큼 **자동으로 깎입니다.**
서베이마다 `date_max = <게시일>` 을 겁니다.

> 이게 없으면 "freshness 를 켰더니 성능이 떨어졌다"는 결론이 나오는데,
> 그건 방법의 문제가 아니라 **평가 설계의 문제**입니다.

한 가지 더 — 날짜는 DB 의 `date` 가 아니라 **arXiv id 의 `YYMM` 에서 유도한 제출일**을
씁니다. `date` 는 v1 게시일이 아니라 **최신 버전 갱신일**이라, 2007년 논문이 2025년에
개정되면 '최신'으로 보입니다. (v1 은 96%가 제출월과 일치하는데 v2+ 는 70%로 떨어집니다.)

## 주 결과 — 토픽 170개 = 정답 집합 전체

`n_papers=1500`, 설정은 **누적**입니다.

| 설정 | R@50 | R@100 | R@500 | R@1500 | nDCG |
|---|---|---|---|---|---|
| dense only (베이스라인) | 15.4% | 21.5% | 36.3% | 38.7% | 0.200 |
| + BM25 | 13.4% | 18.9% | 35.4% | 41.7% | 0.177 |
| + freshness | 14.0% | 20.1% | 36.4% | 41.7% | 0.217 |
| + facets | **19.0%** | **25.5%** | 43.9% | 56.9% | 0.294 |
| **+ facets, BM25 끔 (권장)** | 18.6% | 25.4% | **44.4%** | **57.5%** | **0.299** |

### 단계별 증분

| 단계 | R@50 | R@1500 | nDCG |
|---|---|---|---|
| → + BM25 | −2.0%p | **+3.1%p** | **−0.023** |
| → + freshness | +0.6%p | ±0.0%p | **+0.040** |
| → + facets | **+5.0%p** | **+15.2%p** | **+0.077** |

### 읽는 법 세 줄

**① facet 분해가 압도적입니다.** R@1500 +15.2%p, nDCG +0.077.
나머지 단계를 다 합친 것보다 큽니다. "LLM 이 내놓는 방법론·데이터셋 이름이 dense
임베딩의 사각지대를 정확히 메운다"는 가설이 확인됐습니다.

**② freshness 는 recall 을 안 건드리고 순서만 개선합니다.**
R@1500 은 41.7% 로 같은데 nDCG 는 0.177 → 0.217. **같은 논문을 더 앞에 놓는다**는
뜻이고, 이게 이 프로젝트의 원래 가설이었습니다.

**③ BM25 는 머리를 깎고 꼬리를 늘립니다.** R@50 −2.0%p, R@1500 +3.1%p, nDCG −0.023.
그리고 **facet 을 켜면 아무것도 안 합니다** → [06](06-negative-results.md)

### 표본을 10배로 늘려도 결론이 안 바뀝니다

먼저 16토픽으로 쟀고, 그다음 170토픽 전체로 다시 쟀습니다.
**최대 편차가 facet 의 R@1500 −2.2%p 이고 나머지는 1%p·0.01 이내입니다.**

**표본을 늘려서 달라진 것은 BM25 의 nDCG 하나입니다** — 16토픽에서는 0.189 → 0.189
로 무해해 보였는데, 170토픽에서는 **0.200 → 0.177 로 분명한 손해**입니다.
격차가 작아서 표본이 필요했던 바로 그 항목이고, 이걸 확인하려고 170토픽을 돌렸습니다.

> 발표 포인트: "표본을 늘렸더니 결론이 바뀐 항목이 정확히 하나 있었고, 그게
> 격차가 가장 작던 항목이었다" — 표본 크기를 왜 늘렸는지에 대한 좋은 답입니다.

## 천장 분석 — 검색 병목인가 랭킹 병목인가

정답을 못 맞히는 이유는 둘인데 **처방이 정반대**입니다.
후보 풀에 아예 없으면 **검색** 문제이고, 풀에는 있는데 잘렸으면 **랭킹** 문제입니다.

토픽 16개, `facets+lexical+freshness`, 평균 후보 풀 12,134편:

| 단계 | recall | 무엇이 걸러졌나 |
|---|---|---|
| ① 코퍼스 상한 | 100.0% | 정답이 전부 우리 DB 에 있음 |
| ② 컷오프 상한 | 95.8% | 날짜 컷오프에서 4.2% 탈락 |
| ③ 풀 recall | **77.7%** | ← **검색 손실 18.1%p** |
| ④ 최종 recall | **59.1%** | ← **랭킹 손실 18.6%p** |

**검색과 랭킹이 거의 정확히 반반입니다.** 어느 한쪽만 고쳐서는 절반밖에 못 얻습니다.

### 그리고 검색 손실은 표현이 아니라 **깊이 부족**이었습니다

"후보에 못 들어왔다"도 두 가지일 수 있고 처방이 정반대입니다 —
얕게 판 탓이면 `top_k` 한 줄이면 되고, 초록이 그 논문을 대표 못 하는 것이면
**본문이나 임베딩 교체**가 필요합니다. `top_k` 를 키우며 재면 갈라집니다 (토픽 8개):

| 쿼리당 `top_k` | 평균 후보 풀 | 풀 recall | 증분 |
|---|---|---|---|
| 500 | 3,933 | 73.3% | — |
| **2,000** (기본값) | 13,070 | 84.6% | +11.3%p |
| 8,000 | 42,686 | **91.1%** | +6.5%p |

**`top_k` 를 16배 키우니 +17.8%p 올랐고, 컷오프 상한 95.8% 에 4.7%p 까지 접근했습니다.**
즉 초록으로 도달할 수 없는 몫은 18%p 가 아니라 **약 5%p** 입니다.

> **본문 도입은 지금 우선순위가 아닙니다.** 35GB·수 주가 드는 작업의 상한이 5%p 인데,
> `top_k` 설정 한 줄이 17.8%p 를 줍니다. 본문 논의는 깊이를 충분히 키우고 재랭킹을
> 붙인 뒤 남는 격차를 보고 하는 것이 맞습니다.

⚠ ③④는 표본 16개입니다. ①②는 격차가 커서 뒤집히기 어렵지만 ③④는 표본을 늘려야
확정됩니다. **recall 상한이 100% 가 아니라 약 93% 라는 점도 같이 보세요.**
