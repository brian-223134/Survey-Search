# 8. 예상 질문 — 지금 답할 수 있는 것 / 없는 것

**가장 중요한 원칙**: 아직 안 한 것을 한 것처럼 말하지 마세요.
아래에서 ⚠ 는 **지금 못 하는 주장**입니다.

---

## ⚠ Q. 그래서 서베이 품질이 실제로 좋아졌나?

**지금 할 수 있는 주장**: 검색 품질이 좋아졌습니다. 정답 집합 170토픽에서
R@1500 38.7% → 57.5%, nDCG 0.200 → 0.299.

**아직 못 하는 주장**: 최종 서베이가 좋아졌다.

**왜 아직인가**: 서베이 생성이 편당 실비 $0.3~2 이고 **승인 후에만** 돌립니다.
어댑터 배선은 끝났고(호스트 호출 형태까지 맞춰서 테스트로 고정), 남은 것은
호스트 venv 설치 + 스모크 테스트입니다.

**어떻게 잴 것인가**: 같은 토픽·같은 생성 파이프라인에서 **검색 레이어만 교체**하는
A/B. 그래서 베이스라인 레포를 읽기 전용으로 두고, 드롭인 어댑터로 한 줄만 바꾸는
구조를 만들었습니다.

---

## Q. facet 분해가 대부분이면, 나머지 단계는 왜 만들었나?

**그걸 몰랐기 때문에 만들고 재봤습니다.** 이 질문의 답이 곧 이 프로젝트의 방법론입니다.

- freshness 는 **의도한 대로** 작동합니다 — recall 은 그대로, nDCG +0.040
- BM25 는 facet 없이는 **+3.1%p**, facet 있으면 **0**. 켤지 말지가 **다른 단계에
  의존**한다는 것 자체가 결과입니다
- MMR·재랭킹은 **끄기로 결정한 것이 결과**입니다. 안 재봤으면 켠 채로 보고했을 겁니다

> 그리고 이건 재사용 가능한 지식입니다 — 다른 코퍼스에서 facet 을 못 쓰는 상황이면
> BM25 를 켜야 한다는 것을 **측정 근거를 가지고** 말할 수 있습니다.

---

## Q. LLM 으로 쿼리를 늘리는 건 그냥 query expansion 아닌가?

맞습니다. 새로운 기법이라고 주장하지 않습니다. **기여는 두 가지입니다.**

1. **서베이 검색이라는 태스크에서 얼마나 기여하는지를 정답 기준으로 분리 측정**한 것
   — R@1500 +15.2%p 는 나머지 단계를 다 합친 것보다 큽니다
2. **다른 기법들과의 상호작용**을 잰 것 — facet 을 켜면 BM25 가 무효화되고,
   MMR·재랭킹이 **오히려 해로워집니다.** 이건 각각을 따로 측정해서는 안 나옵니다

---

## Q. 왜 RRF 인가? 학습된 융합(예: LTR)이 더 낫지 않나?

**이 인덱스에서는 점수 융합이 애초에 불가능합니다.** 저장된 문서 벡터는 단위 norm 인데
gte 쿼리 벡터는 정규화돼 있지 않습니다(norm ≈ 24). 한 쿼리 안의 순위는 멀쩡하지만
**쿼리끼리 점수를 비교할 수 없습니다.** BM25 점수는 단위가 아예 다릅니다.

학습된 융합은 가능하지만 **지금 단계에서는 반대 방향**입니다 — 학습을 넣으면
각 단계의 기여를 분해할 수 없습니다. 규칙 기반 ablation 이 먼저입니다.

(그리고 실제로 이걸 확인한 사례가 있습니다: cross-encoder 를 점수로 합쳤다가
**"관련성"이 아니라 "어느 facet 소속인가"로 정렬**되는 결과를 얻었습니다.)

## Q. SimScholarSearch 에서 가져온 게 그게 다인가?

코드 수준으로는 **채점기와 DuckDB FTS 사용법**이고, 이유는 하부 스택이 통째로 다르기
때문입니다(Milvus / BGE-M3 / S2ORC 본문 / verl RL vs FAISS / gte / arXiv 초록 / 규칙 기반).

**다만 가장 중요한 이식이 채점기입니다** — 지표는 실험보다 먼저 고정돼 있어야 합니다.
정답 집합이 아직 없던 시점에 옮겨 뒀고, 그래서 나중에 SurGE 를 붙일 때
recall/nDCG 정의를 **손대지 않고** 쟀습니다. LitSearch → S3 → 여기로 정의가 이어집니다.

설계 수준으로는 RRF k=60 선례, 툴 레지스트리 패턴, 로컬 봉인 코퍼스 원칙.
→ [04-lineage-simscholarsearch.md](04-lineage-simscholarsearch.md)

## Q. RL 로 확장할 생각은?

열려 있고, 안 가는 이유가 셋입니다.

1. 지금은 **각 단계의 기여를 측정하는 단계**입니다. 정책을 학습시키면 분해가 안 됩니다
2. **본문이 없습니다.** "읽고 판단하는 에이전트"가 목표면 본문은 전제인데 초록만 있습니다
3. S3 가 코퍼스를 봉인한 것도 롤아웃마다 API 를 부르면 재현이 안 되기 때문입니다.
   즉 **"온라인으로 가자"와 "RL 로 가자"는 서로 반대 방향의 요구**입니다

만약 간다면 S3 의 툴 9종 시그니처를 따르는 것이 자연스럽습니다.

## Q. 본문(full text)을 넣으면 더 좋아지지 않나?

**측정해 봤고, 지금은 우선순위가 아닙니다.**

검색 손실 18.1%p 를 "표현 문제"와 "깊이 문제"로 나눠 보면,
`top_k` 를 16배 키우는 것만으로 **+17.8%p** 가 회복되고 컷오프 상한 95.8% 에
4.7%p 까지 접근합니다. **초록으로 도달할 수 없는 몫은 약 5%p 입니다.**

본문 도입은 35GB·수 주 작업입니다. 상한 5%p 를 위해 그걸 하는 것보다
깊이를 키우고 재랭킹을 붙인 뒤 **남는 격차를 보고** 판단하는 게 맞습니다.

⚠ 표본 8~16토픽입니다. 확정하려면 표본을 늘려야 합니다.

---

## Q. 평가가 SurGE 하나뿐인데 과적합 아닌가?

**맞습니다. 이게 지금 가장 큰 약점입니다.**

완화하는 요소는 있습니다.
- **정답 집합 전체(170토픽)** 를 씁니다 — 부분표본을 고르지 않았습니다
- 지표는 **외부에서 그대로 이식**했습니다(LitSearch → S3) — 유리한 지표를 고르지 않았습니다
- 하이퍼파라미터를 SurGE 로 튜닝하지 않았습니다. 켜고 끄는 결정만 했습니다

그래도 **다른 벤치마크에서 재확인이 필요합니다.** 정직하게 말하는 게 낫습니다.

---

## Q. 왜 Milvus 를 안 쓰나?

**이 머신에 docker 소켓 권한이 없습니다.** FAISS + DuckDB 로 갔습니다.
성능상 문제는 없습니다 — dense 검색은 전체 지연의 0.1% 였습니다.

---

## Q. GPU 를 안 쓰나?

**쿼리 임베딩에만 씁니다.** FAISS 검색은 GPU 로 8.9배 빨라지지만, 그게
**전체 227초 중 0.145초**라 의미가 없었습니다. 병목은 DB 조회였습니다.

그리고 GPU 는 여러 사람이 공유하는 자원이라 필요 없으면 안 잡는 게 맞습니다.

---

## Q. 재현되나?

**됩니다.** LLM 은 facet 분해에만 쓰고 캐시하며, 온라인 호출도 전부 캐시합니다.

⚠ **다만 2026-08-13 이전에 뽑은 숫자는 재현되지 않습니다.**
DuckDB `ORDER BY` 에 동점 규칙이 없어서 BM25 정렬이 실행마다 흔들렸습니다.
지금은 고쳤고 170토픽 재실행으로 확인했습니다 — R@1500 소수 4자리까지 동일,
nDCG 최대 편차 1.1e-5. 테스트가 붙잡습니다.

> 이건 숨기지 말고 먼저 말하는 게 낫습니다. **"결정적"이라고 문서에 적혀 있다고
> 결정적인 것이 아니었다**는 것 자체가 배울 점입니다.
