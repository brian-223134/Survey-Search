# 7. 엔지니어링 — 시간이 남으면, 질문받으면

발표의 주 내용은 아니지만 **"실험 인프라를 제대로 만들었나"** 를 보여 주는 부분입니다.
슬라이드 한 장 + 백업 슬라이드로 두면 적당합니다.

## ① 검색 1회 227초 → 2.6초

**병목은 dense 검색도 GPU 도 아니었습니다. DB 조회를 두 번, 그것도 해시 조인을 못 쓰는
형태로** 하고 있었습니다.

| | 전 | 후 |
|---|---|---|
| facets + freshness (BM25 켬) | 227.8초 | **13.9초** |
| facets + freshness (BM25 끔) | 114.6초 | **2.6초** |

**검색 품질은 안 바뀌었습니다** — 설정 4개 × 토픽 12개로 nDCG·R@1500 차이 전부 0.

### 두 번 헛짚었습니다 — 이게 발표할 만한 부분입니다

GPU 사용률 0%, CPU 누적 46분. 여기서 **계산 문제라고 단정한 것**이 잘못이었습니다.

**헛짚음 ①** — 로그의 `Could not load library with AVX512/AVX2 support` 를 발견.
CPU(AMD EPYC 9124)는 avx512f 를 지원하는데 `faiss-cpu` 가 SIMD 없는 빌드로 폴백하고
있었습니다. **사실이지만 무관했습니다.**

**헛짚음 ②** — 그래서 GPU 로 옮기면 되겠다고 판단. `faiss-gpu` 가 이 머신에서 실제로
동작하는 것까지 격리 venv 로 확인했습니다. 그런데 재보니:

```
CPU (faiss-cpu, SIMD 없음)   0.145초    ← 쿼리 16개 × top_k 2000
GPU (faiss-gpu)              0.016초    (8.9배)
```

**dense 검색은 전체 227초 중 0.145초, 0.1% 였습니다.**
GPU 로 8.9배를 얻어도 0.13초가 줄 뿐입니다.

> **CPU 가 바쁘다고 계산 문제인 것은 아닙니다.**
> 단계별로 재기 전까지는 전부 추정입니다.

### 실제 병목 — 단계별 `elapsed_s` 를 찍자 바로 드러났습니다

```
--- BM25 켬  합계 218.9s ---
  meta          90.1s (48,214건)
  S5 dedup      90.0s
  S2 dense      30.8s
  S3 lexical     6.7s
```

`meta` 와 `S5 dedup` 이 **82%**. 그리고 둘의 시간이 90.1 / 90.0 으로 거의 같은 것이
단서였습니다 — **같은 일을 두 번** 하고 있었습니다.

**원인 ①: 조인 조건의 `OR` 가 해시 조인을 막고 있었습니다.**

```sql
ON p.paper_id = w.want OR p.base_id = w.want_base   -- 사실상 중첩 루프
```

| 건수 | `OR` | 등호만 |
|---|---|---|
| 1,000 | 0.48s | 0.05s |
| 50,000 | **20.05s** | 0.23s |

**1천 건에서는 눈에 안 띄는데 초선형**이라 후보가 수만 편이 되면 파이프라인을 잡아먹습니다.

> **이건 옳은 수정 두 개가 겹쳐서 생긴 상처입니다.** 원래 등호 조인이었고
> (주석의 "0.1초"가 그때 값), 나중에 S2 API 의 버전 없는 id 문제를 고치며 `OR` 를
> 덧붙이면서 최적화가 **조용히 무효**가 됐습니다.
> **성능 주석에는 언제 잰 값인지 남겨야 합니다.**

**원인 ②: 메타데이터를 두 번 가져오고 있었습니다.** 중복 제거하면서 순서 보존.

## ② 이 저장소는 오랫동안 결정적이지 않았습니다

문서에 **"LLM 은 facet 분해에만 쓰고 캐시하므로 실험도 결정적입니다"** 라고 적혀
있었는데, **사실이 아니었습니다.**

DuckDB `ORDER BY score DESC` 에 **동점 규칙이 없었습니다.** BM25 점수가 부동소수점
끝자리(**8.9e-16**)만큼 흔들리면 순서가 갈리고, `top_k` 경계에서는 **어느 논문이
들어오느냐**까지 바뀝니다.

```sql
ORDER BY round(score, 9) DESC, paper_id LIMIT ?   -- 수정
```

**확인**: 170토픽 전체를 재실행했더니 R@1500 은 소수 4자리까지 동일, nDCG 최대 편차
1.1e-5. `tests/test_determinism.py` 가 이제 붙잡습니다.

> 발표 포인트: **"결정적"이라고 문서에 적혀 있다고 결정적인 것이 아닙니다.**
> 재실행해서 확인하기 전까지는 주장입니다.

## ③ "무음 폐기 금지" 가 실제로 잡은 것들

원칙: **필터·윈도우·컷오프가 버린 논문 수는 반드시 세어서 `stats` 에 남긴다.**

`dropped` 는 `in − out` 을 계산한 값이 아니라 **단계가 스스로 센 값**입니다.
둘이 다르면 그 자체가 버그 신호입니다.

**함정 14가지를 기록해 두었고, 그중 8개가 "예외 없이 결과만 틀리는" 종류입니다.**
대표적인 것들:

| # | 무엇 | 증상 |
|---|---|---|
| 1 | FAISS id 는 1-based | 0-based 로 가정하면 **한 칸 밀린 논문**이 조용히 반환 |
| 2 | `faiss_id − 1` 은 행 번호가 아님 | `id_map` 이 순열이라 **441,842개**가 어긋남 |
| 3 | `citation_count` 가 문자열 | `'9' > '175503'` — 랭킹이 조용히 망가짐 |
| 5 | `date` 는 최신 버전 갱신일 | 2007년 논문이 2025년에 개정되면 '최신'으로 보임 |
| 6 | S2 는 버전 없는 id 를 줌 | **스노우볼링이 0편 기여하고도 조용히** 지나감 |
| 13 | 호스트가 필터를 `**` 로 펼쳐 넘김 | `filter=None` 시그니처만 두면 `**kwargs` 로 빨려 들어가 **조용히 버려짐** |
| 14 | 인용 검증 경로에 **순서 계약** | 본문의 `[1]` 이 다른 논문을 가리키는 서베이가 **편당 $2 에** 나옴 |

**13·14 는 어댑터 배선 문제입니다.** 호스트가 `zip(citations, ids)` 로 인용-논문을
맞추므로 **쿼리 N개 → id N×top_k, 입력 순서**가 계약인데, 이전 어댑터는 N개를 이어
붙여 한 번 검색하고 랭킹 순 목록을 돌려줬습니다.
예외가 안 나면서 **A/B 평가 전체가 틀린 매핑 위에서 계산됩니다.**

> **어댑터를 쓸 때는 호스트의 *호출 형태*까지 봐야 합니다.**
> 시그니처가 맞는 것과 인자가 도착하는 것은 다릅니다.

## ④ 오래 도는 평가를 위한 장치

170토픽 × 4설정 = 검색 680회는 2시간이 넘고, 중간에 죽으면 전부 날아갑니다
(실제로 30토픽분을 날렸습니다).

- **체크포인트** — (설정, 토픽) 쌍 하나가 끝날 때마다 JSONL 한 줄을 `fsync`.
  `kill -9` 로 죽여도 한 줄도 안 잃습니다
- **실험 조건 지문** — 첫 줄에 설정·`n_papers`·컷오프를 박아 두고, 조건이 다른 결과를
  이어붙이려 하면 **거부합니다.** 설정이 섞인 표는 조용히 거짓말을 합니다
- **감시자** — 죽음(60초)과 **정지**(25분)를 구분해 판정하고 재시작

### 왜 "정지"를 따로 봐야 했나 — 함정 10

170토픽 평가가 **CPU 0% · GPU 0% 로 19분** 정지했습니다. 예외는 없었습니다.

`urlopen(timeout=)` 은 호출 전체의 상한이 아니라 **소켓 연산 1회**의 상한입니다.
OpenRouter(Cloudflare 뒤)가 **10초마다 912바이트** keep-alive 를 흘려보내는데,
그때마다 읽기가 성공하니 타이머가 초기화돼 **90초 상한이 영영 발동하지 않습니다.**

```bash
cut -d' ' -f14,15 /proc/<pid>/stat   # CPU 시간이 20초에 0.01초만 늘어남
ss -tnp | grep <pid>                 # 소켓은 ESTAB 로 살아 있음
grep rchar /proc/<pid>/io            # 정확히 10초마다 912바이트씩
```

> **"살아 있는데 아무것도 안 하는" 상태는 `pgrep` 만으로는 절대 안 보입니다.**
> 벽시계 상한을 따로 걸어야 합니다.
